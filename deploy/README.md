# Деплой на VPS

Ветка публикации: `devops-ci-cd`. Каждый push сначала запускает `checks`, затем
`docker`. Только после их успеха задание `deploy` подключается к серверу по SSH.
Pull request и push в другие ветки сервер не обновляют.

## Что обновляется

GitHub собирает Docker-образ, проверяет страницы, CSS, healthcheck и сохранение базы
при пересоздании контейнера. Затем отправляет **этот же образ** с тегом коммита на
VPS. Повторной сборки приложения на сервере нет.

Файлы релиза лежат в `/opt/quiet-queue/releases/COMMIT_SHA`. Исходный git checkout
в `/opt/quiet-queue` не изменяется: созданные вручную production-файлы не конфликтуют
с обновлением. Секреты читаются из существующего `/opt/quiet-queue/.env`.

Перед миграциями скрипт сохраняет проверенный SQLite-снимок через Backup API в
`/opt/quiet-queue/backups`. Это учитывает WAL и работающие подключения. Если копия
не получена, обновление останавливается. Резервная копия находится на том же VPS:
для защиты от потери сервера нужна отдельная выгрузка копий наружу.

Далее выполняются миграции, пересоздаются контейнеры и проверяется `/healthz/`.
Имя Compose-проекта остаётся `quiet-queue`, поэтому сохраняются существующие тома
`quiet-queue_database`, `quiet-queue_caddy_data`, `quiet-queue_caddy_config`.
Одновременные обновления блокируются. Устаревшие коммиты пропускаются до передачи
релиза. Один экземпляр приложения может ненадолго стать недоступным при обновлении.

## Уже подготовленный сервер

- Ubuntu, Docker, Compose, curl и flock доступны.
- Пользователь `deploy` входит в группу `docker`, владеет `/opt/quiet-queue`.
- Его `authorized_keys` содержит открытый ключ для GitHub Actions.
- Контейнер `quiet-queue-web-1` работает, база находится в `/data/db.sqlite3`.
- Созданы repository secrets: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`,
  `DEPLOY_KNOWN_HOSTS`. Последний содержит сохранённую запись ключа SSH-сервера.
  Проверка ключа сервера включена; автоматического доверия новому ключу нет.

Архивы образов в GitHub хранятся 3 дня; после успешной установки архивы на VPS
удаляются. Образы релизов, каталоги релизов и копии базы сохраняются на VPS:
контролируйте свободное место (`df -h`, `docker system df`) и удаляйте старые версии
осознанно. Не запускайте `docker compose down --volumes` на сервере.

## HTTPS и смена домена

Домен по умолчанию: `lev.art184.fvds.ru`. Для смены укажите `SITE_DOMAIN=new.example`
в серверном `.env`, настройте DNS нового домена на VPS и запустите новый деплой.
Порты 80/443 должны быть доступны снаружи.

Успех `deploy` означает, что приложение прошло проверку на VPS. Публичный TLS
проверяется отдельно: общий лимит Let's Encrypt для `fvds.ru` может мешать выдаче
сертификата даже при работающем приложении. Caddy повторяет запросы автоматически.
Сохранённые сертификаты находятся в `caddy_data`; не удаляйте этот том.

Проверка с Mac после получения сертификата:

```bash
curl --fail --show-error https://lev.art184.fvds.ru/healthz/
```

## Проверка установленного релиза

Следующие команды выполняются **на VPS под deploy** после первого успешного CD:

```bash
cd /opt/quiet-queue
sha=$(cat .active-release)
export APP_IMAGE="quiet-queue:$sha"
docker compose --project-name quiet-queue --env-file /opt/quiet-queue/.env \
  -f "releases/$sha/compose.yaml" \
  -f "releases/$sha/compose.production.yaml" \
  -f "releases/$sha/compose.release.yaml" ps
curl --fail http://127.0.0.1:8000/healthz/
```

Для логов замените `ps` на `logs --tail=100 web proxy`.
`.active-release` записывается только после успешной проверки.

## Если обновление не удалось

Откройте логи задания `deploy`. Если ошибка произошла до миграций, приложение
не переключалось. После начала миграций схема базы могла измениться, в том числе
частично: автоматического отката схемы или восстановления базы нет.
Резервная копия сохраняется даже при неудачном обновлении.

Для возврата старого образа сначала выясните, совместим ли он с новой схемой БД.
Если совместим, используйте файлы нужного старого релиза и его `APP_IMAGE`, затем
`docker compose ... up -d --no-build --wait`. При несовместимой схеме нужен
согласованный откат миграций или восстановление снимка при остановленном приложении.
Восстановление снимка удалит данные, записанные после создания копии.
Первый релиз до внедрения CD остаётся в исходном каталоге и локальных Docker-образах.

Повторить текущий релиз можно кнопкой **Re-run all jobs** в GitHub Actions,
если это последний коммит ветки. Не запускайте старый скрипт деплоя для отката:
он снова выполнит миграции.
